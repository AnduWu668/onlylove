# OnlyLove MVP 技术规格

状态：Grill 已完成；本文是实现边界，不包含应用代码。

## 1. 代码与运行形态

- 单仓库 npm workspaces：`web/`、`server/`、`agent/`、`evals/`。
- `web`：Vue 3、Vue Router、Vite、原生 CSS；不引入 Pinia、UI 组件库、PWA 或原生 App。
- `server`：Node.js、TypeScript、Fastify。
- 数据库：PostgreSQL；Drizzle ORM + node-postgres；使用生成并提交的迁移，不在生产使用 schema push。
- Docker Compose 只启动 PostgreSQL；根命令同时启动 Web、Server 和一个 Worker。
- 不使用 Redis、搜索服务、对象存储、外部任务队列、微服务、内部 HTTP 或事件总线。
- 首期不实现或预留照片字段、上传接口和图片处理依赖。

前端使用米白背景、深酒红强调色和低饱和暖灰卡片；移动端优先，不做滑卡和公开市场。成员底部导航为“我的分身 / 候选推荐 / 联系 / 我的”，管理后台使用独立 `/admin`。

## 2. 模块化单体

后端包含七个业务 Module：

- Members：邀请、邮箱登录、成员、基础档案、结构化择偶条件、角色与逻辑注销。
- Portraits：访谈、画像草稿、画像版本、校准、发布、语义特征与证据。
- Matching：硬过滤、待补充条件、配对评估结果、推荐与候选状态。
- Connections：联系请求、唯一当前联系、七日反馈、确认关系和恢复推荐。
- Conversations：INTERVIEW、TWIN、HUMAN 会话及逐条消息、已读状态和 SSE。
- Moderation：失真反馈、屏蔽、举报、处罚、复核和审计。
- Agent Engine：四类 Agent 定义、上下文装配、供应商调用、作业和运行记录。

每个 Module 只直接读写自己拥有的表；跨 Module 数据通过批量、受限的进程内接口获取。一致性操作共享 PostgreSQL 事务。

不创建空的 Admin、Notification 或 Skill Marketplace Module；后台和邮件调用现有 Module 的受限接口。

## 3. 数据形态与版本

- 稳定、可过滤的数据使用关系列：账号、档案、择偶条件、状态、时间、配额、请求和联系。
- `match_profile` 与配对评估输出使用带 `schema_version` 的 JSONB。
- `persona_context` 保存 Markdown 文本，只含提炼语义，不是消息副本。
- 消息逐条保存，INTERVIEW、TWIN、HUMAN 共用会话/消息结构，以类型和授权规则区分。
- 画像版本不可变；成员有草稿指针、当前提交版本和当前发布版本。
- 每个分身会话固定 `profile_version_id`。
- 每个配对结果固定双方画像版本、双方择偶条件版本、匹配规则版本、请求与实际模型版本。

逻辑注销以 `deleted_at` 表示；没有自动物理清除。过去真人消息从成员档案和邮箱脱离后继续保留。所有敏感查看、角色和配置修改写审计记录。

## 4. Agent Engine

使用 `@earendil-works/pi-agent-core` 与 `pi-ai`，只作为 Agent 循环和模型适配运行时。不加载 Pi Coding Agent 的文件、Shell、任意上传或动态 Skill 能力。

业务接口仅有：

- `continueInterview`
- `extractPortrait`
- `replyAsTwin`
- `evaluatePair`

每次调用临时创建 Agent，从业务数据库恢复最小上下文，写回结果后销毁；不为每名成员运行长期进程。

四类 Agent 定义均版本化，包含角色、Prompt 文件、允许工具、输出 Schema、主模型和备用模型。初始四类角色使用同一模型作为可比基线，最终按 benchmark 决定。

### 4.1 上下文隔离

- 画像访谈员：当前 `persona_context`、当前 `match_profile`、画像草稿和当前访谈近期消息。
- 画像提取器：当前画像、草稿及本次新增访谈消息。
- 公开恋爱分身：会话固定的 `persona_context`、允许公开的基础资料和当前分身会话。
- 配对评估 Agent：双方 `match_profile`、结构化择偶条件和匹配评判规则。

公开分身从查询层就拿不到隐藏标签、匹配分、内部 Prompt、原始访谈或其他访客记录。提示注入防护不能只依赖 Prompt 拒绝。

单次输入采用应用级可配置预算，初始 32K token；预计到约 24K 时形成画像检查点并使用最新语义记忆与近期消息继续。上线前必须通过 16K/32K/64K 长对话 benchmark 决定正式值。

### 4.2 模型接入与故障

- 初始供应商为火山方舟，使用固定主模型 ID；备用模型必须通过同角色 benchmark。
- 模型配置从环境变量读取；API key 永不进入数据库、仓库、测试数据、响应或日志。
- 自动测试使用确定性假模型。真实方舟评测由显式命令触发，缺少环境变量时立即失败；产品运行不静默退回假模型。
- 主模型只可在尚未输出或后台任务尚未写入结果时整体切换备用模型；禁止流式生成中途拼接两个模型。
- 结构化输出先校验 Schema；失败时把错误交给同一模型修复一次，第二次失败则任务失败。
- 每次结果记录实际供应商和模型，不用 `latest` 作为可审计版本。

### 4.3 运行记录与费用

每次模型调用落库：Agent 角色、任务 ID、成员/会话/画像/规则版本引用、供应商、请求模型、实际模型、输入 token、输出 token、延迟、重试、备用切换、错误和估算人民币成本。

估算成本使用带生效日期的模型单价配置；供应商账单是最终费用依据。普通管理员查看获授权任务明细，超级管理员查看全站按日期、角色、供应商和模型聚合的 token、费用、延迟、失败和切换。

## 5. 异步任务与实时消息

- 成员消息使用 HTTP POST 提交。
- Agent 流式回答和真人新消息使用 SSE 接收；MVP 不使用 WebSocket。
- 画像提交、配对评估等慢任务写 PostgreSQL 作业表，由单 Worker 处理。
- 作业自动重试最多三次，随后进入管理员失败任务列表；管理员只能重试，不能修改任务输入或输出。
- 会话和 Agent 输出必须幂等，客户端重试不能重复扣额度、重复保存消息或重复创建联系。

## 6. 配额、推荐与并发约束

- 候选分身默认每名发起者每天 50 条；自己的 Agent 默认每天 100 条；北京时间零点重置，不结转。
- 成员消息落库时原子预占额度；同一消息的模型重试不再扣，最终任务失败退款。
- 每日推荐上限 N 同时是每日新增和未处理候选容量；成员每天至多主动补充一次，旧候选占用容量。
- 不用低于阈值的候选补数。
- 建立当前联系使用数据库唯一约束和事务竞争：首个成功的双方接受获胜，其余请求中性取消。
- 屏蔽、逻辑注销、撤回发布和条件修改都必须在推荐与发送入口再次校验，不能只依赖旧页面状态。

## 7. 权限边界

- 成员不能读取或直接修改隐藏画像、标签、权重、特征证据、数字匹配分和完整配对理由。
- 联系请求前，分身主人只能按随机会话 ID 查看只读原文；请求后只增加请求者候选卡关联。
- 普通管理员只能通过案件或任务权限查看相应数据。
- 超级管理员可查看任意聊天、隐藏画像和匹配分，但每次敏感访问必须审计；不提供全站聊天信息流。
- 分身主人永远不能在访客与分身的记录中代替分身回复。

## 8. 邮件与通知

邮件使用通用 SMTP 适配。开发环境把验证码写到服务端控制台；测试使用内存 Mailer。邮件仅用于验证码、联系请求、接受、七日回访和审核决定；真人新消息只有站内未读。

## 9. 最小自动检查

实现时至少保留少量可运行的关键检查：

- 邀请和 OTP 的过期、单次使用与尝试次数；
- 隐藏画像与分身上下文的授权隔离；
- 消息额度的并发扣减与失败退款；
- 画像版本不可变、会话固定版本；
- 硬条件和待补充条件；
- 唯一当前联系的并发竞争；
- 屏蔽、注销和撤回发布立即阻断新动作；
- Agent Schema 失败重试一次及主备切换边界。
