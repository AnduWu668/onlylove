# OnlyLove MVP 产品规格

状态：Grill 已完成；本文记录已确认需求，不代表已经实现。

## 1. 目标与边界

OnlyLove 面向中国大陆、年满 18 岁、认真寻找长期异性关系的成员。核心假设不是“算法能直接找到灵魂伴侣”，而是：准确的恋爱分身能让候选人在真人接触前，以较低成本感受对方的价值判断、关系边界、推理方式和表达风格。

MVP 是前后端分离、适配手机浏览器的 Web 产品。除真人照片明确后置外，需走通注册、画像、分身、匹配、联系、真人聊天、反馈、审核和管理后台完整闭环。

后置：真人照片、交友模式、Agent-Agent 对话、Skill 市场与上传、群聊、原生 App、PWA、复杂安全策略和备案工作。MVP 候选卡使用昵称占位头像，不预留照片字段或空接口。

## 2. 成员入口与账号

- 仅邀请注册；邀请绑定邮箱、单次使用、七天过期，管理员可撤销或重新签发。
- 邮箱验证码为六位数字、十分钟有效、最多尝试五次、六十秒后可重发；数据库只保存哈希。
- 不设密码。成员使用邮箱验证码登录。
- 首个超级管理员邮箱由部署配置指定。
- 逻辑注销后立即禁止登录、推荐、请求和当前联系；管理员可恢复或永久清除，记录保留期间原邮箱不可重新注册。
- 已注销成员过去发送的真人消息为对方保留，但与可访问档案和邮箱脱离，显示为“已注销成员”。

## 3. 基础资料与结构化择偶条件

基础档案由成员直接维护：昵称、出生日期、性别、身高、当前城市、职业。婚姻状态、有无子女、是否希望生育不进入 MVP 表单。

结构化择偶条件由成员直接维护并参与匹配：

- 希望匹配的性别：MVP 仅支持异性匹配，属于硬条件。
- 年龄范围：可不限，也可选择必须满足或只是偏好。
- 身高范围：可不限，也可选择必须满足或只是偏好。
- 可接受城市：多选，属于双方互相满足的硬条件；不限制为单一城市。
- 职业要求：可不限，或填写简短要求并选择必须满足或只是偏好。

成员修改条件后，系统立即重新检查尚未处理的候选；不再满足硬条件的候选被移除，满足者保留。修改不影响已经建立的真人联系，之后的推荐记录条件版本。

## 4. 形成恋爱分身

### 4.1 固定访谈

成员先完成十道固定访谈题。题目提供三至四个参考选项，覆盖讨喜、不讨喜、中性或矛盾但现实的方向；选项不标优劣并随机排序。成员可以多选、组合、选择“都不符合”或自由补充。

### 4.2 动态引导完善

完成固定题后，画像访谈员继续以类似 Grill 的方式主动提问。选题优先级为：

1. 成员指出“不像我”的内容；
2. 低置信度关系维度；
3. 信息矛盾；
4. 已发布问题规划规则中的模型共性弱项。

问题规划规则必须版本化。离线 benchmark 只能暴露弱项，不能直接在线修改 Prompt。

八个关系维度固定为：长期规划、价值观、关系边界、沟通方式、冲突修复、情感支持、生活方式、家庭与财务。

每个维度内部至少保存：自我倾向、伴侣期望、硬边界、重要程度、低/中/高置信度和证据消息引用。低置信度内容不能参与配对评分。

非基本关系特征只能由 Agent 从成员对话中提取。成员不能填写或直接修改隐藏标签，也看不到具体语义、权重、理由和证据。新证据使内部特征达到中或高置信度时，只反馈“我对你的理解又清楚了一些”并更新总体进度 `x/8`。

原始消息逐条保存在数据库。画像语义文档只保存提炼后的有用信息，不是原始聊天 Markdown。

### 4.3 草稿、提交、校准与发布

- 对话期间维护一个内部画像草稿，不为每条消息创建正式版本。
- 成员满意后手动点击“提交本次理解”，生成不可变的待校准画像版本。
- 形成画像的访谈题不得再次作为校准题。
- 校准使用十道未见场景：八个关系维度各一道，另有两道跨维度冲突场景。
- 每题展示场景和当前分身预测回答，成员选择“像我 / 部分像我 / 不像我”；后两项通过聚焦追问、多个方向和自由补充完成纠正。
- 至少八题“像我”且没有关键事实捏造，才达到发布门槛。未达到时显示“分身还需要继续了解你”，不是用户答错。
- 纠正进入画像草稿；重新提交后使用同维度新场景，不复用已经作答的失败场景。
- 通过校准后，成员仍需主动点击“发布分身”。提交不等于发布。
- 更新已发布分身时，旧版本继续服务；新版本发布后原子替换。成员可先主动撤回旧版本。

## 5. 分身行为

- 成员界面只有“我的分身”入口，但聊天标题明确区分私有画像访谈员和公开恋爱分身。
- 成员可以与自己的恋爱分身对话并纠正理解。
- 候选人可以在申请真人联系前与对方恋爱分身对话。
- 聊天页持续标明 AI 身份。分身可以用第一人称表达有依据的价值判断和偏好。
- 分身不能安排见面、提供联系方式、作出承诺、确认关系或代表主人接受联系。
- 对画像未覆盖的问题，可以明确不确定地推测倾向，但不能编造具体经历、事实或现实计划。
- 公开分身不能取得隐藏匹配档案、匹配分、内部 Prompt、其他访客会话或原始访谈记录。
- 每段分身会话固定开始时的画像版本，进行中不热切换。

## 6. 分身聊天可见性与额度

- 访客进入候选分身会话前，必须明确同意完整原文会提供给分身主人。
- 发出联系请求前，主人只看到只读原文和随机会话编号，不能看到访客账号或候选卡；主人不能在该会话回复。
- 发出请求后，接收方才可把原匿名会话和请求者候选卡关联；任何阶段均不展示隐藏标签、匹配分或完整内部理由。
- MVP 不做原文脱敏，入口提醒访客不要输入不愿提供给主人的个人信息。
- 主人不会因为有人开始聊分身而收到通知；只有联系请求触发通知。
- 候选分身额度按发起聊天的成员计，所有候选共享每天 50 条；自己的画像访谈员和分身共享另一个每天 100 条额度。
- 北京时间零点重置，不结转。每条被系统接受的成员消息预占一次；同一消息的重试和备用模型切换不重复计数，最终生成失败则退回。
- 超级管理员可调整两类全站额度，修改和敏感访问均留审计记录。

## 7. 匹配与推荐

### 7.1 候选生成

成员必须满足：八个关系维度均为中或高置信度、校准至少 8/10、没有关键事实捏造、分身已发布、没有当前真人联系。

确定性过滤先处理：双方希望匹配性别、年龄和身高硬范围、双方当前城市与可接受城市、屏蔽关系、账号及当前联系状态。职业硬条件和语义硬边界交给配对评估 Agent；证据不足时标记“待补充条件”，暂不推荐，并向缺信息的一方提出不暴露候选人的补充问题。

成员每天至多主动获取一次推荐。超级管理员配置每日/未处理候选共同上限 N 和最低互惠适合度；旧的未处理候选占用容量，不用低于阈值的人补足。

系统只展示适合该成员的候选，不展示全市场。数据较少时可以通过配置增加展示量，但不能绕过最低阈值。

### 7.2 配对评估

配对评估 Agent 只读取双方匹配档案、结构化条件和版本化匹配评判规则，不读取原始聊天。

它逐维度输出：A 对 B、B 对 A、互动理由以及是否存在硬边界冲突；维度按个人重要程度加权。双方总方向适合度用调和平均形成互惠适合度，避免单向高分掩盖另一方低分。相似、互补和复杂互动均可产生高或低结果，不采用“越相似越好”的统一假设。

模型输出必须符合结构 Schema；失败后把校验错误交给同一模型重试一次，第二次失败则任务失败。每次结果必须记录双方画像版本、条件版本、规则版本和实际模型版本，保证结果可以审计和复现。

具体阈值不预设，由 benchmark 分布决定初值；超级管理员可以调整并记录版本和审计。

### 7.3 展示与候选状态

候选卡展示昵称、年龄、身高、当前城市、职业和安全推荐理由，使用昵称占位头像。它不展示生日、邮箱、可接受城市、隐藏标签、数字分或完整内部理由。

- 成员可以同时保留并与多个候选分身聊天。
- 跳过后，在任一方画像或结构化条件未改变前不再推荐同一组合。
- 联系请求七天未处理则过期，不算拒绝；版本未改变前不再推荐。
- 屏蔽永久压制组合。

## 8. 真人联系

- A 与 B 的分身聊天后可以发出联系请求。B 看到 A 的候选卡，也可以先与 A 的分身聊天，再接受或拒绝。
- 同一成员只能有一个当前 1v1 真人联系。第一个双方接受的请求建立联系，其余待处理请求以中性文案取消，不算拒绝。
- 真人消息必须在平台内发送；HTTP 提交、实时接收。平台不主动显示联系方式，也不阻止成年人自行发送联系方式。
- 真人新消息只产生站内未读，不发邮件。
- 建立联系第七天，双方分别选择继续了解、结束接触或提出确认关系；未反馈不自动结束。
- 任一方选择结束即结束当前联系，并可单独完成接触复盘、更新画像、重新校准后恢复推荐。
- 确认关系需要一方提出、另一方接受；确认后暂停推荐。关系结束后需要复盘和校准，再主动恢复。

## 9. 反馈、举报与治理

- “分身回答不准确”是质量反馈：关联具体消息，推动主人纠正并进入质量指标，但不自动改画像、降匹配分或处罚。
- “故意夸大或欺骗”使用举报：管理员查看证据后决定驳回、警告、限期停用或永久封禁。
- 屏蔽和举报是独立动作；屏蔽立即终止请求或当前联系并永久抑制双方再次推荐。
- 举报案件记录理由和证据。成员可发起复核，复核创建新的审核案件。
- 普通管理员管理邀请、举报处罚、案件关联聊天和失败 Agent 任务重试。
- 超级管理员还可查看任意聊天、隐藏画像和匹配分，调整推荐与额度配置，恢复或永久清除成员并管理普通管理员；所有敏感访问被审计。

## 10. 通知与后台指标

邮件只用于：验证码、联系请求、请求接受、七日回访和审核决定。

后台展示：

- 注册、画像进度、校准、发布和推荐资格状态；
- 获取推荐、无候选、联系请求、接受、当前联系、结束、确认关系；
- 七日双向继续率；
- 分身校准通过率、关键事实捏造、候选失真反馈；
- Agent 错误、重试、备用模型切换、延迟；
- 按日期、Agent 角色、供应商和模型汇总的输入/输出 token 与估算人民币成本。

普通管理员只能查看其有权处理任务的运行明细；超级管理员可查看全站聚合和全部明细。

## 11. MVP 验收闭环

除照片外，以下路径必须完整可运行：

1. 超级管理员创建普通管理员并签发邀请；
2. 两名成员通过邮箱验证码注册并填写档案与择偶条件；
3. 双方完成固定访谈、动态完善、手动提交、校准和发布；
4. 系统完成结构化过滤、LLM 配对评估和推荐；
5. A 与 B 的分身聊天并申请真人联系，B 与 A 的分身聊天后接受；
6. 双方进行站内真人聊天并完成七日继续/结束/确认关系流程；
7. 成员完成失真反馈、屏蔽或举报，管理员完成审核处置；
8. 超级管理员能查看配置、任务、匹配依据、Token 与成本；
9. 结束或确认关系后的推荐状态符合上述规则。

## 12. 实施时配置，不是未决需求

- 火山方舟主模型和备用模型的准确 ID、API key；模型必须先通过对应角色 benchmark。
- 匹配评判规则 v0 的具体文字和经 benchmark 得到的最低阈值。
- 每日推荐上限 N。
- SMTP 服务器配置。
- 首批邀请成员和管理员邮箱。

这些值允许在实施或内测前确定，不改变本文产品行为。
