## Problem Statement

认真寻找长期关系的用户，通常要在大量浅层资料和重复寒暄中投入时间，却仍然难以判断双方在价值观、关系边界、沟通方式、冲突修复和生活选择上是否真正适合。传统婚恋产品依赖基础筛选或简单标签，无法表达由深层经历形成的语义特征，也无法让用户在真人接触前低成本感受“这个人可能怎样理解、判断和表达”。

OnlyLove 需要验证一个核心产品假设：通过持续访谈形成足够准确、明确标注为 AI 且不代表本人承诺的恋爱分身，再结合双向结构化条件和语义配对评估，可以帮助成员更有效地选择值得真人了解的候选人。MVP 必须走通除照片外的完整闭环，并通过 benchmark、校准反馈、七日双向继续率和 Token 成本证明这套方式是否值得继续投入。

## Solution

构建一个面向中国大陆成年异性长期关系场景的移动端 Web 产品。成员通过邀请和邮箱验证码注册，维护基础档案及结构化择偶条件；画像访谈员先用十道固定题降低表达门槛，再用类似 Grill 的动态追问持续形成隐藏画像草稿。成员手动提交后，系统生成不可变画像版本和恋爱分身，并通过十道未见场景校准分身是否像本人。通过校准且由成员主动发布后，系统才允许该成员进入推荐。

推荐先使用代码处理可确定的硬条件，再由内部配对评估 Agent 按版本化匹配评判规则，分别判断双方方向适合度、互动适合度和硬边界。成员只能看到基本候选卡和安全推荐理由，不能看到隐藏标签、数字分或完整内部理由。成员可以先与候选人的恋爱分身交流，再发起真人联系；双方同意后进入平台内唯一的 1v1 真人会话，并在七日回访中选择继续、结束或确认关系。

系统提供普通管理员与超级管理员、举报与处罚、逻辑注销、Agent 作业重试、Token 和成本观测。首期使用火山方舟固定模型，通过 Pi Core 承载四类 Agent；真实模型与匹配规则必须由同仓库 benchmark 验证。

## User Stories

1. 作为超级管理员，我希望通过部署配置建立首个超级管理员身份，以便系统无需预置公开管理账号。
2. 作为管理员，我希望为指定邮箱签发单次邀请，以便控制首批内测成员范围。
3. 作为管理员，我希望邀请在七天后自动失效，以便过期链接不能长期流通。
4. 作为管理员，我希望撤销尚未使用的邀请，以便及时收回错误或不再需要的准入资格。
5. 作为管理员，我希望为同一邮箱重新签发邀请，以便处理邀请过期或遗失。
6. 作为受邀成员，我希望通过六位邮箱验证码注册和登录，以便无需维护密码。
7. 作为成员，我希望验证码十分钟有效且六十秒后可重发，以便兼顾安全和可用性。
8. 作为成员，我希望验证码连续错误达到五次后失效，以便降低暴力尝试风险。
9. 作为成员，我希望只有年满 18 岁才能参加匹配，以便产品限定为成年人长期关系场景。
10. 作为成员，我希望能退出登录而不改变画像或关系状态，以便安全结束当前设备会话。
11. 作为成员，我希望填写昵称、出生日期、性别、身高、当前城市和职业，以便建立简洁的基础档案。
12. 作为成员，我希望不被要求填写婚姻状态、有无子女和生育意愿，以便 MVP 聚焦已确认的核心信息。
13. 作为成员，我希望直接维护希望匹配的性别，以便不由 Agent 猜测这一稳定条件。
14. 作为成员，我希望设置或不限伴侣年龄范围，以便明确表达稳定年龄条件。
15. 作为成员，我希望设置或不限伴侣身高范围，以便明确表达稳定身高条件。
16. 作为成员，我希望维护多个可接受城市，以便匹配不局限于单一城市。
17. 作为成员，我希望填写或不限职业要求，以便系统在匹配时考虑稳定职业偏好。
18. 作为成员，我希望能把年龄、身高和职业要求声明为“必须满足”或“只是偏好”，以便区分排除条件和加分项。
19. 作为成员，我希望修改结构化择偶条件后未处理候选立即重新校验，以便列表反映我的当前要求。
20. 作为成员，我希望修改择偶条件不影响已经建立的真人联系，以便关系进程不会被配置变化意外终止。
21. 作为新成员，我希望先完成十道固定访谈题，以便以可控负担开始建立恋爱分身。
22. 作为新成员，我希望每题有三至四个现实参考选项，以便不必从空白文本开始组织回答。
23. 作为成员，我希望参考选项同时包含讨喜、不讨喜、中性和矛盾倾向，以便系统鼓励真实而不是社会期许答案。
24. 作为成员，我希望参考选项不标注好坏并随机排序，以便降低被暗示选择“优质人设”的风险。
25. 作为成员，我希望能多选、组合、选择“都不符合”或自由补充，以便表达参考选项之外的真实情况。
26. 作为成员，我希望固定访谈后由画像访谈员主动提出聚焦问题，以便逐步补全难以一次描述的关系特征。
27. 作为成员，我希望画像访谈员优先询问我指出“不像我”的内容，以便纠正分身最明显的偏差。
28. 作为成员，我希望画像访谈员优先追问低置信度、矛盾和缺失信息，以便提高画像可靠度。
29. 作为成员，我希望系统在真正获得可靠新理解时给出一般性正反馈，以便知道对话正在产生效果。
30. 作为成员，我希望只看到整体画像进度而不是具体隐藏标签，以便了解完成度但不能直接操纵匹配表征。
31. 作为成员，我希望非基本关系特征只能由 Agent 从对话中提取，以便不能通过直接编辑标签欺骗系统。
32. 作为成员，我希望能通过持续对话影响画像草稿，以便系统理解真实语境而不是只依赖一次问卷。
33. 作为成员，我希望原始访谈消息被完整保留，以便后续纠正、审计和重新提取有可靠来源。
34. 作为成员，我希望画像语义文档只保存提炼后的有用信息，以便它不是一份重复的逐字聊天导出。
35. 作为成员，我希望手动提交画像草稿，以便由我决定何时形成正式版本。
36. 作为成员，我希望提交画像不会自动发布分身，以便我能先验证分身表现。
37. 作为成员，我希望每次提交形成不可变画像版本，以便历史回答和匹配结果可以复现。
38. 作为成员，我希望使用十道未见场景校准分身，以便验证它能泛化而不是复述训练问题。
39. 作为成员，我希望校准覆盖八个关系维度和两个跨维度冲突场景，以便评估范围足够完整。
40. 作为成员，我希望看到当前分身对校准场景的预测回答，以便判断它是否像我。
41. 作为成员，我希望能选择“像我、部分像我、不像我”并补充纠正，以便低成本提供准确反馈。
42. 作为成员，我希望至少八题像我且没有关键事实捏造后才能发布，以便候选接触到的分身具备最低可信度。
43. 作为成员，我希望未达到门槛时看到“分身还需要继续了解你”，以便不会误以为自己回答错误。
44. 作为成员，我希望重新校准使用新的同维度场景，以便分身不能靠记住原题通过。
45. 作为成员，我希望校准通过后仍需主动发布，以便我明确同意参与推荐和候选分身会话。
46. 作为已发布成员，我希望更新画像期间旧版本继续服务，以便改进过程不会无意造成中断。
47. 作为成员，我希望可以先撤回旧分身，以便严重失真时立即停止新的推荐和分身会话。
48. 作为成员，我希望与自己的画像访谈员和恋爱分身聊天时明确看到当前角色，以便不会混淆采访与公开表达。
49. 作为成员，我希望通过与自己的恋爱分身聊天纠正理解，以便持续提高分身相似度。
50. 作为候选人，我希望公开恋爱分身始终标明 AI 身份，以便不会把回答误认为真人即时消息。
51. 作为候选人，我希望恋爱分身能用第一人称表达有依据的价值判断和偏好，以便感受到接近本人的交流风格。
52. 作为候选人，我希望恋爱分身不能替主人安排见面、提供联系方式、作出承诺或确认关系，以便 AI 不越过真人决定边界。
53. 作为候选人，我希望分身对未知事实明确表达不确定，以便不会把模型推测误认为真实经历。
54. 作为分身主人，我希望公开分身拿不到隐藏匹配档案、原始访谈和其他访客会话，以便提示注入也无法泄露这些数据。
55. 作为候选人，我希望同一分身会话固定开始时的画像版本，以便对话中不会突然人格变化。
56. 作为成员，我希望自己的 Agent 每天有独立的 100 条消息额度，以便画像完善不会占用候选探索额度。
57. 作为成员，我希望所有候选分身共享每天 50 条消息额度，以便成本可控且不能通过切换候选无限聊天。
58. 作为成员，我希望模型重试不重复扣额度且最终失败退回，以便平台故障不会消耗我的次数。
59. 作为候选访客，我希望进入分身会话前明确知道完整原文会提供给主人，以便我能决定是否继续。
60. 作为分身主人，我希望在联系请求前只能看到匿名只读记录，以便能了解分身表现但不能识别访客。
61. 作为分身主人，我希望不能在访客与分身的记录中回复，以便不会发生隐蔽真人代聊。
62. 作为分身主人，我希望只有收到联系请求时才看到请求者候选卡，以便匿名阶段不泄露访客身份。
63. 作为成员，我希望有人开始与我的分身聊天时不收到通知，以便避免无意义打扰。
64. 作为成员，我希望联系请求、接受、七日回访和审核决定可以通过邮件通知，以便不错过关键事件。
65. 作为成员，我希望真人新消息只显示站内未读，以便邮件不会被高频聊天淹没。
66. 作为符合推荐资格的成员，我希望主动获取符合最低阈值的候选，以便系统不会自动无休止推送。
67. 作为成员，我希望只看到适合我的候选而不是完整市场，以便产品聚焦质量而非刷卡浏览。
68. 作为成员，我希望系统不用低于阈值的人补足数量，以便推荐不足时保持诚实。
69. 作为成员，我希望旧的未处理候选占用推荐容量，以便不能无限累计候选。
70. 作为成员，我希望性别、年龄、身高、城市、屏蔽和联系状态先由确定性规则过滤，以便明确条件不依赖模型猜测。
71. 作为成员，我希望职业和深层语义条件由配对评估 Agent 依据证据判断，以便复杂要求不被字符串比较误解。
72. 作为成员，我希望语义硬边界证据不足时暂不推荐并追加匿名补充问题，以便系统不擅自假设满足或冲突。
73. 作为成员，我希望配对评估分别判断我对候选和候选对我的适合度，以便严重单向关系不会被包装成高匹配。
74. 作为成员，我希望相似、互补和复杂互动都依据具体语境判断，以便系统不使用单一“越像越好”公式。
75. 作为成员，我希望候选卡只显示昵称、年龄、身高、城市、职业和安全推荐理由，以便了解基本信息但不泄露内部算法。
76. 作为成员，我希望候选卡不显示隐藏标签、数字分或完整内部理由，以便防止算法被操纵或反向推断。
77. 作为成员，我希望能跳过候选，以便在画像和条件不变时不再收到同一组合。
78. 作为成员，我希望屏蔽某人后永久停止双方推荐和当前互动，以便立即建立个人边界。
79. 作为成员，我希望能同时与多个候选分身交流，以便真人联系前进行比较。
80. 作为成员，我希望与候选分身交流后发起真人联系请求，以便先了解再接触。

86. 作为已建立联系的成员，我希望在平台内进行 1v1 真人聊天，以便复盘、屏蔽、举报和安全审计有连续上下文。
87. 作为已建立联系的成员，我希望平台不主动展示联系方式但也不拦截成年人自行发送，以便安全边界不过度干涉交流。
88. 作为已建立联系的成员，我希望第七天分别选择继续、结束或提出确认关系，以便系统获得真实的双向继续指标。
89. 作为未完成七日反馈的成员，我希望系统记录未反馈而不自动结束，以便沉默不被错误解释。

92. 作为当前联系成员，我希望确认关系需要一方提出、另一方接受，以便单方操作不能代表双方。
93. 作为确认关系的成员，我希望停止候选推荐，以便产品尊重当前关系状态。
94. 作为关系结束的成员，我希望复盘和重新校准后主动恢复推荐，以便画像更新后再进入下一轮。
95. 作为候选人，我希望能关联具体分身消息提交“不准确”反馈，以便平台和主人改善分身质量。
96. 作为分身主人，我希望单次不准确反馈不会自动改画像或处罚我，以便普通理解误差可以通过对话纠正。
97. 作为候选人，我希望故意夸大或欺骗使用独立举报流程，以便严重问题进入人工判断。
98. 作为成员，我希望屏蔽和举报可以独立选择，以便立即保护自己而不必一定提交案件。

101. 作为普通管理员，我希望只能查看案件关联聊天和获授权任务，以便管理权限保持最小化。
102. 作为普通管理员，我希望能重试失败 Agent 任务但不能修改输入输出，以便恢复服务而不篡改记录。
103. 作为超级管理员，我希望查看任意聊天、隐藏画像、匹配分和 Agent 运行明细，以便诊断核心质量问题。
104. 作为超级管理员，我希望调整推荐数量、阈值和两类 Agent 额度，以便内测期间控制供给、质量和成本。
105. 作为超级管理员，我希望管理普通管理员并恢复或永久清除成员，以便承担全站治理责任。
106. 作为平台负责人，我希望所有敏感访问和配置修改被审计，以便追踪内部数据使用。
107. 作为成员，我希望逻辑注销后立即停止登录、推荐、请求和当前联系，以便账号退出即时生效。
108. 作为真人聊天对方，我希望已注销成员的历史消息仍可阅读但不再连接其档案，以便对话上下文不被破坏。
109. 作为平台负责人，我希望每次模型调用记录角色、模型、Token、延迟、重试、错误和估算成本，以便比较模型并控制费用。
110. 作为超级管理员，我希望按日期、角色、供应商和模型查看 Token 与成本聚合，以便找到最昂贵或最不稳定的 Agent。
111. 作为平台负责人，我希望分身校准、关键事实捏造和失真反馈进入质量指标，以便核心卖点可以被检验。
112. 作为平台负责人，我希望七日双向继续率作为匹配主指标，以便避免用点击率冒充关系质量。

## Implementation Decisions

- MVP 面向中国大陆、年满 18 岁、认真寻找长期异性关系的成员；产品不声称能够保证找到灵魂伴侣。
- MVP 为移动端优先的前后端分离 Web 产品，不做公开市场和滑卡。
- 使用单仓库 npm workspaces，包含 Web、Server、Agent 和 Evals 四个工作区。
- 前端使用 Vue 3、Vue Router、Vite 和原生 CSS；不引入 Pinia、UI 组件库或 PWA。
- 后端使用 Node.js、TypeScript 和 Fastify；PostgreSQL 使用 Drizzle ORM 与 node-postgres。
- 使用模块化单体和一个 PostgreSQL 数据库；不拆微服务、内部 HTTP 或事件总线。
- 七个业务 Module 为 Members、Portraits、Matching、Connections、Conversations、Moderation 和 Agent Engine；每个 Module 只直接访问自己的表，通过批量进程内接口取得其他数据。
- INTERVIEW、TWIN、HUMAN 使用统一会话/消息结构，通过会话类型和授权规则区分。
- 稳定字段使用关系列；匹配档案和 LLM 配对结果使用带 Schema 版本的 JSONB；分身上下文使用 Markdown 文本。
- 原始消息保存在数据库，不生成原始聊天 Markdown；分身上下文只保存提炼后的语义信息。
- 基础档案与结构化择偶条件由成员直接维护；隐藏语义特征由 Agent 提取，成员不能直接编辑。
- 画像草稿可持续更新；只有成员手动提交才生成不可变画像版本，只有校准通过并主动发布才进入推荐。
- 固定访谈题和未见校准场景完全分离；校准门槛为至少 8/10 且没有关键事实捏造。
- 画像、条件、匹配评判规则、Agent 定义、Prompt、Schema 和模型全部版本化；每次结果记录其实际版本。
- Agent Engine 仅暴露 `continueInterview`、`extractPortrait`、`replyAsTwin` 和 `evaluatePair` 四个业务接口。
- 使用 Pi Core 与 pi-ai 承载 Agent 循环，不加载文件、Shell、任意上传或动态 Skill 能力。
- 画像访谈员、画像提取器、恋爱分身、配对评估 Agent 分别装配最小上下文；公开分身从数据查询层拿不到隐藏匹配数据。
- 单次模型输入初始预算 32K Token，约 24K 形成检查点；正式预算由 16K/32K/64K benchmark 决定。
- 初始供应商为火山方舟；主模型与备用模型使用固定 ID，备用模型必须通过同角色 benchmark。
- 主备切换只能发生在尚未输出或后台任务尚未写入结果时，禁止流式中途拼接模型。
- 结构化模型输出进行 Schema 校验；把错误交给同一模型修复一次，第二次失败则任务失败。
- 每次模型调用落库角色、任务、画像/规则版本、供应商、请求与实际模型、输入/输出 Token、延迟、重试、主备切换、错误和估算人民币成本。
- API key 仅来自环境变量，不进入仓库、数据库、测试数据、响应或日志。自动测试使用确定性假模型；真实方舟评测由显式命令触发。
- 确定性硬条件由代码过滤；职业和语义互动由配对评估 Agent 按版本化规则判断。硬边界所需信息不足时进入待补充状态。
- 配对评估按八个维度分别输出 A→B、B→A 和互动理由，按个人重要程度加权，使用调和平均形成互惠适合度。
- 候选只看到基本资料和安全推荐理由；隐藏标签、数字分和完整内部理由只在授权后台使用。
- 成员每天至多主动获取一次推荐；每日新增数量与未处理候选容量共用 N，不以低分候选补足。
- 候选分身每天 50 条、自己的 Agent 每天 100 条，北京时间零点重置；消息原子预占，最终失败退款。
- 访客进入分身会话前必须同意原文提供给主人。请求前匿名，请求后只关联候选卡，主人始终只能只读。
- 成员消息通过 HTTP POST 提交；Agent 流式回答和真人新消息通过 SSE 接收，不使用 WebSocket。
- 慢任务使用 PostgreSQL 作业表和单 Worker；自动重试最多三次，之后进入管理员失败列表。
- 当前真人联系通过数据库唯一约束和事务保证每名成员最多一段；并发接受只允许一个请求获胜。
- 真人聊天保留在平台内；平台不主动展示联系方式，也不拦截成年人自行发送。
- 屏蔽立即终止互动并永久压制组合；举报独立进入人工案件。
- 普通管理员与超级管理员分权；超级管理员的全局敏感访问和所有配置修改必须审计。
- 邮件使用通用 SMTP；开发环境可把验证码写到服务端控制台。邮件只用于验证码、联系请求、接受、七日回访和审核决定。
- 根开发命令同时启动 Web、Server 和 Worker；Docker Compose 只提供 PostgreSQL。
- 首期不实现或预留真人照片字段、上传接口和图片处理依赖；候选卡使用昵称占位头像。
- 视觉使用米白、深酒红和低饱和暖灰，底部导航为“我的分身 / 候选推荐 / 联系 / 我的”，后台位于独立管理入口。
- 个人信息和模型处理保持在中国大陆；更换供应商必须继续满足该数据边界。

## Testing Decisions

- 测试只断言成员、管理员或外部业务接口可观察到的行为，不断言内部函数调用次数、Prompt 私有措辞或 ORM 实现细节。
- 最高测试 seam 是一个移动端双成员端到端闭环：邀请注册、访谈、提交、校准、发布、推荐、双向分身聊天、联系、真人聊天和七日状态。
- 第二个 seam 是七个 Module 的公开进程内业务接口；跨 Module 规则通过接口与真实 PostgreSQL 集成测试验证，不直接测试私有表查询。
- 第三个 seam 是 Agent Engine 的四个业务接口；自动测试注入确定性假模型，真实方舟 benchmark 使用相同接口。
- 仓库当前没有既有应用代码或测试 prior art；测试风格以本规格、领域术语和 ADR 为基准，不虚构已有模式。
- Members 测试邀请绑定、过期、撤销、单次使用、OTP 哈希、有效期、尝试次数、重发间隔、角色和逻辑注销。
- Portraits 测试固定题与校准题隔离、草稿不参与推荐、手动提交、版本不可变、8/10 门槛、关键事实捏造硬失败、发布和撤回。
- Portraits 测试成员只能看到 `x/8` 和一般性正反馈，不能读取或修改隐藏标签、权重、理由和证据。
- Agent 上下文授权测试必须证明公开分身无法取得隐藏匹配档案、原始访谈、系统 Prompt 和其他访客会话。
- Conversations 测试 INTERVIEW、TWIN、HUMAN 的参与者、可见性、请求前匿名、请求后候选卡关联和主人只读约束。
- 配额测试使用并发请求验证原子预占、重试不重扣、最终失败退款、北京时间重置和两个额度池隔离。
- Matching 测试确定性性别、年龄、身高、城市、屏蔽和当前联系过滤。
- Matching 测试职业或语义硬条件缺失返回待补充，不默认通过或排除。
- Matching benchmark 测试排序和不变量而不是固定精确分：硬边界冲突排除、双向高于严重单向、一方极低不能被平均掩盖、低置信度不主导。
- Matching 测试候选安全理由不包含隐藏标签、数字分、敏感经历和完整内部理由。
- Connections 使用真实数据库事务测试并发接受，保证每名成员最多一个当前联系，其余请求中性取消。
- Connections 测试七日未反馈不自动结束、任一方结束立即生效、确认关系必须双方同意、确认后暂停推荐。
- Moderation 测试失真反馈不自动改画像或处罚，举报创建案件，屏蔽立即生效，处罚与复核记录理由和证据。
- 权限测试覆盖成员、普通管理员和超级管理员；任何越权读取隐藏画像、聊天或匹配分必须失败。
- 审计测试验证超级管理员敏感读取、角色修改、推荐配置和额度配置都会产生记录。
- Agent 作业测试自动重试三次、人工重试不修改输入输出、Schema 修复只允许一次、主备模型不在流式中途切换。
- Token 观测测试验证输入/输出 Token、模型版本、延迟、重试、切换和估算成本落库并按权限聚合展示。
- Benchmark 使用版本化合成数据，不把真实成员原文作为默认测试资料。
- 画像访谈 benchmark 检查追问相关性、非诱导参考选项、矛盾处理和未知保持。
- 画像提取 benchmark 检查八维覆盖、证据引用、置信度、事实与推断分离以及公开上下文边界。
- 恋爱分身 benchmark 检查未知场景相似度、关键事实捏造、承诺边界、提示注入和跨会话窃取。
- 配对 benchmark 至少包含 20–30 个合成组合，覆盖硬边界、互惠与单向、低置信度、相似、互补和复杂互动。
- 对同一长对话分别测试 16K、32K、64K 上下文预算，质量无显著下降时选择更低成本配置。
- 真实模型评测记录实际模型 ID、Prompt/规则/Schema 版本、Token、延迟和费用；模型或规则变化后必须重新运行。
- 真实模型 benchmark 不放入每次 CI 默认流程，避免费用和随机波动阻断确定性检查。
- 最低发布验收为除照片外完整双人闭环以及管理员、审核、任务和 Token 后台可操作。

## Out of Scope

- 真人照片上传、压缩、核验、存储以及相关数据库预留。
- 交友模式及其持续推荐语义；MVP 仅实现婚恋模式。
- Agent-Agent 对话、成员分身自动与候选分身对话。
- Skill 市场、Skill 上传、动态加载第三方恋爱 Skill。
- 群聊。
- 原生 iOS/Android App、PWA 和推送通知。
- 公开全市场、滑卡和无限刷新。
- 用户直接查看或编辑隐藏标签、语义特征、权重、证据和数字匹配分。
- 向成员承诺算法可以找到灵魂伴侣或给出关系成功概率。
- 身份、职业、年龄、照片或成员自述的外部真实性核验。
- Redis、对象存储、搜索服务、外部消息队列、微服务和事件总线。
- Prompt 可视化编辑器和管理员直接修改 Agent 任务输入输出。
- 复杂内容安全、自动脱敏、完整反欺诈、备案和对外正式发布流程；仅保留已确认的 MVP 安全与治理能力。
- 自动物理删除策略；MVP 使用逻辑注销，永久清除由超级管理员决定。
- 将真实亲密对话发送给未确认中国大陆数据边界和训练条款的模型供应商。

## Further Notes

- 产品最重要的评测对象是恋爱分身准确度，不是界面完成度或模型聊天自然度。
- 初始模型供应商为火山方舟，具体主模型和备用模型 ID 在实施时由 API key 配置和 benchmark 决定。
- API key、SMTP、首批管理员邮箱、每日推荐 N、匹配规则 v0 和初始阈值属于实施时配置，不是未决产品需求。
- 匹配评判规则 v0 需要覆盖八个维度、结构化条件、双向期望、置信度、重要程度、硬边界、待补充条件、相似/互补/复杂互动和安全推荐理由。
- 线上首要匹配指标为七日双向继续率；分身质量同时观察校准通过率、关键事实捏造和失真反馈。
- 推荐结果不能以“灵魂契合”“成功概率”或确定性关系结论对外表达。
- 测试 seam 已由此前设计确认：完整产品闭环、模块公开接口、四个 Agent Engine 业务方法。没有为测试额外引入更低层抽象。
- 本规格遵循项目领域术语和现有 ADR；若未来改变数据地域、隐藏画像控制权、分身会话可见性、站内真人聊天或模块化单体，需要显式更新相应 ADR。
