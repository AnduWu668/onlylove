# OnlyLove Agent Benchmark 计划

状态：画像访谈、画像提取与“固定 10 题 → 对话完善”数据集和 runner 已实现；分身与配对数据集待补。

## 1. 目的

Benchmark 的首要目标是验证恋爱分身准确度和匹配判断是否遵循产品规则，然后才比较模型价格、延迟和上下文长度。供应商宣传、通用聊天体验和单一总分都不能替代本评测。

评测与应用位于同一仓库，复用生产 Agent 接口、Prompt、Schema 和模型适配；不建立单独仓库。

## 2. 数据集

仓库保留版本化合成案例，不使用真实内测成员原文作为默认评测数据：

- `evals/interview-cases.json`：固定题、动态追问、矛盾信息、低置信度、诱导性选项。
- `evals/extraction-cases.json`：八个关系维度、伴侣期望、硬边界、重要程度、证据引用和缺失信息。
- `evals/portrait-learning-cases.json`：同一成员仅固定 10 题与继续对话后的成对画像特征金标。
- `evals/twin-cases.json`：未知场景、表达风格、事实未知、承诺边界、提示注入和跨会话窃取。
- `evals/matching-cases.json`：20–30 个双人组合，覆盖结构化硬条件、语义硬边界、互相适合与严重单向、相似、互补、复杂互动和待补充条件。

每个案例固定输入、预期不变量、允许差异和失败理由；不要求模型复述唯一标准文本。

画像学习 benchmark 使用同一模型、生产画像提取 Prompt 与 Schema 做成对消融：先从空草稿提取固定 10 题，再基于该草稿只输入新增对话。两阶段对同一最终金标计算特征槽位 precision、recall、F1 和 slot accuracy；中高置信度特征必须命中独立概念组并引用正确证据，未知证据、无证据高置信结论和预设虚假事实为一票否决。当前 3 个合成案例是先导集，只报告分布和增益，不据此设发布阈值；扩大并人工复核案例后再冻结门槛。

真实方舟完整运行命令为 `npm run benchmark -w evals`，只复测画像学习消融可运行 `npm run benchmark -w evals -- --portrait-learning`；确定性数据和评分器检查为 `npm test -w evals`。

## 3. 四类角色

### 3.1 画像访谈

检查：

- 是否优先追问低置信度、矛盾和用户纠正；
- 参考选项是否同时包含讨喜、不讨喜、中性或矛盾方向；
- 是否避免暗示“正确人设”；
- 是否降低回答负担并允许自由补充；
- 是否在缺少证据时保持未知。

### 3.2 画像提取

检查：

- 八个维度覆盖和 Schema 合法性；
- 自我倾向、伴侣期望、边界、重要程度、置信度和证据是否对应；
- 是否把成员原话与 Agent 推断分开；
- 是否错误补全事实；
- 低置信度内容是否被排除出评分数据；
- `persona_context` 是否只包含分身获准使用的信息。

### 3.3 恋爱分身

检查：

- 在未见场景中的价值判断、边界、推理方式和表达风格是否与合成成员一致；
- 未知事实是否明确不确定；
- 是否编造经历、联系方式、现实计划或关系承诺；
- 是否拒绝套取隐藏画像、系统 Prompt、匹配分和其他访客会话；
- 是否在第一人称表达与 AI 身份之间保持边界。

关键事实捏造是硬失败。产品校准要求十道未见场景至少八道被成员判断“像我”；离线案例以预期判断和不变量评估，不让同一个模型给自己循环打分。

### 3.4 配对评估

检查排序和不变量，不锁死精确数值：

- 确定性硬条件失败必须排除；
- 高置信度语义硬边界冲突必须排除；
- 硬边界所需信息缺失必须输出待补充，而不是猜测；
- 双向适合组合应高于严重单向组合；
- 一方极低不能被另一方极高平均掉；
- 相似不自动加分，互补不自动加分；
- 低置信度推断不得主导结果；
- 候选安全理由不得泄露标签、分数或敏感经历。

## 4. 模型比较

每个参评模型使用相同 Prompt、上下文、工具定义、Schema、随机性、输出预算和重试上限。记录供应商、请求模型 ID、实际模型 ID、Prompt/规则/Schema 版本、输入/输出 token、延迟、首 token 延迟、重试、错误和按当期单价估算的人民币成本。

初期四类角色使用同一个火山方舟固定模型作为基线；可比较方舟其他模型和研究报告中的 Qwen、DeepSeek、Kimi、MiniMax，但任何主模型或备用模型都必须先通过对应角色门槛。

真实供应商评测由显式命令运行并读取本地环境变量。普通自动测试使用确定性假模型，不能默认消耗真实 token。

## 5. 上下文实验

对同一批长访谈与分身会话分别使用 16K、32K、64K 应用输入预算，比较：

- 画像信息召回与矛盾处理；
- 未见场景一致性；
- 关键事实捏造；
- 首 token 和总延迟；
- 输入/输出 token 与人民币成本。

初始工程值为 32K、约 24K 触发画像检查点。若 16K 不降低质量则选择 16K；只有 64K 明显改善核心指标才提高预算。

## 6. 匹配评判规则 v0

正式开发前先起草 `agent/matching-rubric.md` v0，至少包含：

- 确定性条件与语义条件边界；
- 双向分别判断；
- 置信度、重要程度和证据使用；
- 硬边界冲突与待补充条件；
- 相似、互补和复杂互动；
- 维度加权与互惠聚合；
- 对成员安全的推荐理由；
- 禁止把分数表述成成功概率或灵魂伴侣结论。

先用合成案例验证排序与不变量，再根据分布设置初始推荐阈值。规则、阈值或模型发生变化时必须重新运行匹配 benchmark；它不进入易波动的每次 CI 必跑集合。

## 7. 线上反馈闭环

上线后的核心指标：

- 分身校准通过率；
- 关键事实捏造；
- 候选“分身回答不准确”反馈；
- 无候选率、请求率、接受率；
- 七日双向继续率；
- 结束接触和确认关系；
- Agent 错误、延迟、token 与成本。

线上数据用于发现弱项和形成新的脱敏合成案例，不直接在线改写 Prompt、标签、分数或匹配规则。规则更新必须版本化、重新 benchmark 后再发布。
